# Decisions

## D1 — Scope: one platform, three tenants
- The capstone: one Kubernetes platform that hosts the workloads of Projects 3, 4 and 5 (ticket triage, the Arabic voice assistant, the meeting summarizer) as tenants, first on minikube, then on AKS. The platform owns the cluster, admission policy, tenancy (namespaces, RBAC, quotas, network policy), identity, secrets and private networking; each tenant owns its code and its chart.
- What it adds over the three projects: the private networking they left out (Project 3 D15, Project 5: private endpoints and VNet integration → Project 7), one admission policy for every tenant, and workload identity plus Key Vault CSI as the only way a tenant reaches Azure.
- Same rule as before: what runs on the laptop runs on Azure; only configuration differs.

## D2 — This repo holds the platform; tenant code stays in its repos
- `secure-ai-platform`: cluster IaC (M5), the policy library (`policy/`), platform manifests (`platform/`), tenant onboarding (namespaces, RBAC, quotas, identities), the deploy glue, and the checks that the platform behaves the same on minikube and AKS.
- Tenant images are built and published by their own repos (GHCR today; the platform's ACR on AKS, M5); this repo pins which versions it runs.

## D3 — Tenancy: one namespace per tenant, labelled with its owner
- Namespaces `triage`, `voice`, `meetings` (generated from `platform/tenants.yaml` since M2, D15), each labelled `platform.lab/tenant`, `platform.lab/owner` and `platform.lab/source` (the repo). `platform.lab` is a label prefix of this lab, not a domain anyone owns.
- Platform namespaces (Kubernetes', the CNI's, Gatekeeper's) are listed in the namespace rule's parameters; every other namespace is a tenant's and must say so (D7).

## D4 — Rules judge the workload, not only the pod
- `policy/gatekeeper/lib/workload.rego` finds the pod spec in a Pod, in the pod template of a Deployment, StatefulSet, DaemonSet, ReplicaSet or Job, and in a CronJob's job template. A bad Deployment is refused when it is applied, with the reason on the operator's screen, instead of being accepted and then failing to create pods (the ReplicaSet controller's error is only in events).
- `containers` = containers and init containers (both can set resources); `all_containers` adds ephemeral containers (`kubectl debug`), which run images too.

## D5 — Gatekeeper, rules as sources, three checks of the same cases
- Engine on the laptop: OPA Gatekeeper **3.23.1** (latest stable on 2026-11-25; 3.24.0 is in beta), Helm chart 3.23.1 (`platform/gatekeeper/values.yaml`).
- One directory per rule (`policy/gatekeeper/rules/<rule>/`: `rule.yaml`, `rule.rego`, `constraint.yaml`, `cases/`). `scripts/build_policy.py` generates the ConstraintTemplates (`policy/gatekeeper/templates/`, Rego and libs embedded) and gator's test suite (`policy/gatekeeper/suite.yaml`); both are committed, never edited by hand, and a unit test fails when they are stale.
- Rego is written in the syntax both Rego versions accept (`import future.keywords.*`, `contains` / `if`), so the same template loads in Gatekeeper's default (v0) mode and in any engine that only speaks v1.
- Every case is checked three ways: **regopy** evaluates the generated templates' Rego in the unit tests (no cluster, no gator); **gator verify** runs the suite in CI; **`scripts/live_cases.py`** sends each case to a live cluster with `kubectl apply --dry-run=server` (all admission runs, nothing is stored) and requires a disallowed case to be denied by its own constraint alone. `scripts/policy_must_fail.py` weakens the policy, the tenancy objects and (since M3) the tenant releases one way at a time (14 mutations in M1, 27 in M2, 37 since M3) and requires the unit tests (and gator, in CI, for the rules) to catch each.
- **On AKS (proposed, decided in M5):** the Azure Policy add-on, which runs its own managed Gatekeeper, with these templates as custom policy definitions (`templateInfo.sourceType: Base64Encoded`, generated from the same files). Open Gatekeeper and the add-on are not run together; the add-on's Gatekeeper version and its support for `libs` are checked then.

## D6 — Images: from the platform's registries, with a version
- Every image starts with an allowed prefix (now `ghcr.io/salmanamn/` and `mcr.microsoft.com/`; the platform's ACR joins in M5) and names a version: a digest, or a tag other than `latest`. The tag is read from the part after the last `/`, so a registry port is never taken for a tag.
- Prefixes end with `/` (schema `pattern` and a unit test), so `ghcr.io/salmanamn/` does not admit `ghcr.io/salmanamnx/`.
- Ephemeral containers are in the rule (D4's `all_containers`) and reach Gatekeeper through the `pods/ephemeralcontainers` subresource (D10). They have no case file, because the API server refuses them on create; `scripts/check_tenancy.py`'s debug section checks them live (D20).
- **Status:** proven on the cluster (M2, `docs/evidence/m2-tenancy.txt`): `kubectl debug --profile=restricted` with a docker.io image is refused by `platform-allowed-images`, with an MCR image admitted.

## D7 — Pod security is Pod Security Admission at "restricted"; Gatekeeper makes it mandatory
- Pod-level security (privileged, host namespaces and paths, capabilities, non-root, seccomp, privilege escalation) is Kubernetes' built-in Pod Security Admission at `restricted`, which minikube and AKS both run, rather than a second copy of the same checks in Rego.
- What Gatekeeper adds: no tenant namespace can opt out. `platform-tenant-namespace` refuses a namespace without the owner labels or without `restricted` for all three modes (`enforce` blocks pods, `warn` shows the reason when a Deployment is applied, `audit` records it).

## D8 — Containers request CPU and memory and limit memory; no CPU limit
- `platform-container-resources`: every container and init container sets `requests.cpu`, `requests.memory` and `limits.memory`. No CPU limit is required: throttling hurts latency (Project 4's turn budget), and the namespace quota (M2) caps a tenant's total.

## D9 — Pods mount no Kubernetes API token
- `platform-no-sa-token`: the pod spec sets `automountServiceAccountToken: false`. Tenant workloads never call the Kubernetes API; on AKS they reach Azure through workload identity, whose token is a separate projected volume (Project 4 M8 ran without a Kubernetes token). The pod's field is required, not the service account's, because the pod's overrides it.
- Consequence for M3: the Functions host must not keep its keys in Kubernetes secrets (`AzureWebJobsSecretStorageType=kubernetes` needs the API); it uses files.

## D10 — Admission fails closed for tenants, never for the cluster itself
- The validating webhook's failure policy is `Fail`: when Gatekeeper is down, tenant workloads cannot be created or changed. With one replica on the laptop that is a real outage; it is the intended trade (AKS sizing in M5).
- **The webhook only sees what the constraints judge** (`validatingWebhookCustomRules`): Pods (and `pods/ephemeralcontainers`, D6), Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, CronJobs and Namespaces, and since M2 NetworkPolicies and RoleBindings (D18, D19), CREATE and UPDATE. The chart's default sends every resource, cluster-scoped ones included, so with `Fail` a stopped Gatekeeper blocked everything outside the exempt namespaces — on 2026-11-26 it blocked Helm's own `ClusterRole` for the Gatekeeper upgrade (a deadlock: the fix could not be installed while the webhook waited for it), and it would block node leases in `kube-node-lease`. A unit test keeps the rules equal to the constraints' kinds and refuses wildcards.
- `kube-system` carries `admission.gatekeeper.sh/ignore` (chart: `controllerManager.exemptNamespaces` plus `postInstall.labelNamespace.extraNamespaces`), so the webhook never sees the cluster's own pods and an outage cannot stop them; `gatekeeper-system` is exempt by the chart. The constraints exclude both again, which keeps them out of the audit too.

## D11 — The laptop cluster: minikube, Kubernetes 1.36, Calico
- Profile `aiplat` (`scripts/cluster.sh`), Kubernetes **v1.36.4**: the minor version Project 4 ran on AKS (its D53: 1.36 until azurerm can set the node pool's LocalDNS profile; 1.37 became GA and LTS on AKS in October 2026, checked again in M5). Calico for NetworkPolicy (M2), metrics-server; 4 CPUs, 6 GB.
- kubectl 1.37 talks to 1.36 within the supported skew.

## D12 — Tool versions in one file; gator pinned by checksum
- `versions.env` holds the Gatekeeper version, gator's SHA-256 (of `gator-v3.23.1-linux-amd64.tar.gz` from the GitHub release, taken 2026-11-25), the Kubernetes version and the minikube profile. `scripts/install-gator.sh` checks the archive before unpacking it, on the laptop and in CI.

## D13 — A decisions index from day one
- `docs/decisions-index.md` is generated from the headings of this file by `scripts/decisions_index.py` (Project 5's script, its D11), and `tests/unit/test_decisions.py` fails when the index is stale or a number is missing or repeated. A decision's status lives in the decision (`- **Status:** …`); updates are new decisions whose heading says `(updates Dx)`.

## D14 — CI and branch protection from the first milestone
- `.github/workflows/ci.yml`: `lint` (ruff, generated files and decisions index current, shellcheck, actionlint), `unit` (pytest: every case through regopy, the decisions drift test), `policy` (gator verify, then `policy_must_fail.py --require-gator`). `permissions: contents: read`, no secrets.
- `main` protected by `scripts/protect-main.sh` (Project 5's) with those three checks once they are green.

## D15 — Tenancy objects are generated from one spec
- `platform/tenants.yaml` lists the tenants (name, source repo, owner, quota) and the per-container limits; `scripts/build_platform.py` writes `platform/generated/<tenant>.yaml`: Namespace, ResourceQuota, LimitRange, two RoleBindings, two NetworkPolicies, in apply order, each labelled `platform.lab/managed=true`. Generated files are committed, never edited by hand, and a unit test (and CI's `lint`) fails when they are stale. They replace M1's hand-written `platform/namespaces/tenants.yaml`.
- The platform's own objects obey the platform's policy: the unit tests run every Gatekeeper rule over every generated object and over `platform/cluster/roles.yaml`.

## D16 — The platform's own tenant roles, not the built-in ones
- `platform/cluster/roles.yaml`: `platform-tenant-admin` and `platform-tenant-reader`, bound per namespace to the groups `tenant:<tenant>:admins` and `tenant:<tenant>:readers`; `platform-operators` binds the group `platform:operators` to `cluster-admin`. On AKS the groups become Entra ID groups (M5).
- Built-in `admin` is not used: it can write NetworkPolicies, Roles and RoleBindings and read Secrets, so a tenant could open its own network or grant itself more. The tenant admin runs its workloads (pods, deployments, statefulsets, jobs, cronjobs, services, configmaps, PVCs, HPAs, PDBs, exec, logs, port-forward, `kubectl debug`) and reads its quota, limits, network policies and bindings; it gets no Secrets (Key Vault CSI on AKS, M5), no DaemonSets, nothing outside its namespace. No role uses a wildcard (unit test).
- `platform/checks/rbac-matrix.yaml` (31 rows in M2, 33 since M3: no ScaledObjects, no Secrets in `keda`) says who may do what. It is checked offline against these objects by a small RBAC evaluator in `tests/unit/test_platform.py`, and live with `kubectl auth can-i --as … --as-group …` (D20).

## D17 — Quotas and limits: caps, no defaults
- Each tenant's ResourceQuota caps `requests.cpu`, `requests.memory`, `limits.memory` and `pods` (laptop sizes; AKS sizes in M5) and sets `services.loadbalancers` and `services.nodeports` to 0: a tenant can't expose itself outside the cluster, and Kubernetes enforces that natively, so no Gatekeeper rule is needed for it.
- The LimitRange sets only a per-container `max` (2 CPUs, 4 Gi). No `default` or `defaultRequest`: LimitRange defaults are filled in before validation, so they would satisfy `platform-container-resources` (D8) for a container that never asked for anything (unit test).
- **Status:** proven on the cluster (M2, `docs/evidence/m2-tenancy.txt`): Kubernetes 1.36 checks both the ResourceQuota and the LimitRange on `kubectl apply --dry-run=server`, so the five admission cases refuse or admit without creating anything.

## D18 — Network: every tenant starts closed; tenant policies stay inside the tenant
- Each tenant namespace gets `platform-default-deny` (all ingress and egress) and `platform-allow-dns` (UDP and TCP 53 to `kube-dns` in `kube-system`). Nothing else is open, not even between pods of the same tenant: a tenant's own policies open what it needs.
- Tenant admins can't write NetworkPolicies (D16); tenant policies (the voice chart's, for instance) arrive through the platform's deploy path and must pass `platform-tenant-network-policy`: peers are the namespace's own pods (podSelector only), a namespace in `egressNamespaces` named exactly by `kubernetes.io/metadata.name` (`kube-system`), or on egress an `ipBlock` whose CIDR is one of that tenant's `egressCIDRs` exactly (string equality: rego-cpp, the unit tests' engine, has no `net.cidr_contains`; exact matches are also the stricter rule). No rule without `from` or `to` (it would match everything).
- `egressCIDRs` today: `triage: [192.168.49.1/32]`, the laptop as seen from minikube's docker network, for Project 3's emulators in M3. Other tenants get theirs when their milestone needs them.
- The webhook now also sends NetworkPolicies and RoleBindings (D10's rules and test).

## D19 — Tenant role bindings grant tenant roles to that tenant only
- `platform-tenant-role-binding`: a RoleBinding in a tenant namespace refers to `platform-tenant-admin` or `platform-tenant-reader` (ClusterRoles only, no namespaced Roles) and binds only groups `tenant:<namespace>:…` or service accounts of the same namespace; no users. The platform's generated bindings pass it (D15); a mistaken binding by an operator does not.
- Cluster-wide bindings (ClusterRoleBindings) stay outside the webhook's scope (D10: cluster-scoped objects are never blocked by a stopped Gatekeeper); the RBAC matrix checks that no tenant group holds a cluster-wide permission.

## D20 — The live tenancy check
- `scripts/check_tenancy.py` runs four sections and writes one evidence file: **rbac** (every matrix row through `kubectl auth can-i` with impersonation), **admission** (`platform/checks/admission/`: a pod within limits admitted; a container over the LimitRange max, a pod over the tenant's CPU quota, a NodePort and a LoadBalancer Service refused by the quota or limits and not by Gatekeeper), **network** (probe pods in `triage` and `voice`; round 1 = the baseline, round 2 after `platform/checks/netpol-probe-allow.yaml` opens one flow in `triage`), **debug** (an ephemeral container through `kubectl debug --profile=restricted`: from docker.io refused by `platform-allowed-images`, from the allowed registry admitted; D6).
- Probe image: `mcr.microsoft.com/azurelinux/base/python:3.12.16-2-azl3.0.20261120` (Azure Linux 3.0, from an allowed registry, Python for the socket checks and `http.server`), run as user 65532 with Pod Security `restricted` settings and a read-only root filesystem. The unit tests run every Gatekeeper rule over the probe pods and the check objects, so a refusal in the live check can't come from the platform's own policy by mistake.

## D21 — Evidence only from a cluster that answered before and after the run (updates D5, D20)
- `scripts/live_cases.py` and `scripts/check_tenancy.py` ask `kubectl get --raw /readyz` before they start and again before they write evidence (`scripts/cluster_ready.py`). Not ready before: one `FAIL the API server is not ready …` line, exit 2, nothing sent. Not answering at the end: the results are printed, then `FAIL the API server stopped answering during the run …`, exit 2, and no evidence file is written.
- Why: the laptop cluster dropped in the middle of a run twice (M1 once, M2 once: 39 connection errors as `FAIL` lines). Those files looked like evidence. Unit tests (`tests/unit/test_cluster_ready.py`) feed both scripts a fake kubectl for the three cases, and a must-fail mutation removes the check.

## D22 — KEDA is a platform component, and reads no tenant's Secrets
- KEDA **2.21.1** (chart and app; latest on 2026-11-27, released 2026-11-16) in namespace `keda`, installed by `./scripts/platform.sh keda` with `platform/keda/values.yaml`. Tenants get event-driven scaling, scale to zero included, without running anything cluster-wide themselves. On AKS the KEDA add-on takes its place (M5).
- `keda` is a platform namespace (D3, D10): in every constraint's `excludedNamespaces`, in `platform-tenant-namespace`'s `platformNamespaces`, exempt from the webhook (`controllerManager.exemptNamespaces` + the ignore label), so a Gatekeeper outage can't stop the autoscaler. The platform creates it (`platform/cluster/namespaces.yaml`, Pod Security enforce `baseline`, warn and audit `restricted`) before Gatekeeper's post-install job labels it. A unit test keeps the lists in step.
- `permissions.operator.restrict.secret` and `permissions.metricServer.restrict.secret`: KEDA reads Secrets in its own namespace only. A tenant's scaler authenticates through a **ClusterTriggerAuthentication** (`platform/keda/trigger-authentications.yaml`) whose Secret the operator keeps in `keda` (D26), never through a tenant's Secret. And `rbac.enabledCustomScaledRefKinds: false`: the chart default `scaledRefKinds` (`*` in `*`) gives the operator `get` on every resource in every namespace, Secrets included, which `restrict.secret` does not touch (found by `check_triage.py` on 2026-11-28). Only Deployments and StatefulSets are scaled here, and they need no extra rule. Tenant admins can't create ScaledObjects (no `keda.sh` rule in D16; a matrix row): the platform's deploy path applies them.

## D23 — Tenant data services on the laptop: a range on minikube's network (updates D18)
- M2 gave triage `192.168.49.1/32`, the gateway of minikube's docker network, meaning "the laptop". It doesn't work and isn't narrow: Project 3's compose publishes its ports on `127.0.0.1` only, which the gateway address doesn't reach, and the gateway is the whole Docker host, every published port of every lab.
- Instead the tenant's emulators join minikube's network: ticket-triage-agent's `docker-compose.cluster.yml` puts Service Bus, Cosmos, Azurite and Mailpit at `192.168.58.101`–`.104` (their ports stay on 127.0.0.1 for the laptop's scripts), and triage's `egressCIDRs` is `192.168.58.96/28`. Pods reach them through Calico's NAT to the node; the NetworkPolicy sees the real destination. A case refuses the gateway, and the tenant's own policy narrows the range to the emulators' ports.
- The profile's network on the laptop is `192.168.58.0/24` (checked 2026-11-27 in Step 17: another minikube profile took `192.168.49.0/24` first), so the addresses are in `.58`. They follow the network: a cluster on another subnet needs the same change in the release, the network-policy constraint and its cases, `check_triage.py`, `policy_must_fail.py` and the tenant's `docker-compose.cluster.yml`; Step 17's check stops before anything uses the range.

## D24 — Tenant ingress from platform namespaces, named exactly (updates D18)
- `platform-tenant-network-policy` takes `ingressNamespaces` (now `keda`): an ingress peer may be the namespace's own pods or a namespace from that list, named by `kubernetes.io/metadata.name` only (optionally with a podSelector), the same shape as egress namespaces. KEDA's operator polls the triage tenant's queue-depth endpoint (D27); nothing else outside a tenant may connect to it. Other labels can be set by whoever owns a namespace, so they are refused (case).

## D25 — Tenant releases: the tenant's own chart at a pinned commit, rendered and committed
- `platform/releases/<tenant>.yaml`: the tenant's chart (repository, full commit id, path), its image by digest, and the platform's values for this cluster. `scripts/pin_release.py <tenant>` writes the tenant repo's `main` commit and the digest CI published from it (`sha-<12>` tag). `scripts/render_tenants.py` fetches the chart at that commit (`.cache/tenants/`, by commit id) and renders it with `helm template` at the Helm version in `versions.env` (**v4.3.2**; any other version is refused, so renders don't drift) to `platform/rendered/<tenant>.yaml`, with a header naming chart, commit, image and Helm. Committed; CI's `lint` re-renders (`--check`).
- The tenant owns its chart (D1, D2); the platform owns the values and is what applies the result (`./scripts/platform.sh tenant <name>`, as operator: tenant admins can't write NetworkPolicies, D16/D18). Nothing is exempt: the unit tests run every Gatekeeper rule over every rendered object, then check what the rules don't say: only the tenant's namespace and the kinds ConfigMap, Deployment, Service, ScaledObject, NetworkPolicy (no Secret, no RBAC); ClusterIP Services only; every container on the pinned image; no secret-like setting in a ConfigMap; every Secret and key a pod reads is one the operator creates (D26), with a key file for every function it loads; the scaler through a ClusterTriggerAuthentication (D22); the lab addresses inside the tenant's range and used by its settings; the release at full scale plus one rolling-update pod within the quota (D27). Must-fail mutations weaken the release file, the rendered file and the KEDA settings.

## D26 — Tenant Secrets are the operator's: on the laptop, emulator keys and random host keys
- `scripts/tenant_secrets.py <tenant>` (run by `platform.sh tenant`) writes, from the release: the tenant's settings Secret (on the laptop: the emulators' published development keys, Azurite's taken from the Azure Storage SDK's own source, at the release's `lab` addresses, plus random values for the Event Grid stub's topic key and the fake LLM's key), the Functions host keys Secret (random; one file per function the release loads, plus master, default, KEDA's and the Event Grid system key: ticket-triage-agent D28), and KEDA's copy of its host key in `keda` (D22).
- Values never appear on a command line, in output or on disk (manifests go to kubectl on stdin, base64); existing values are kept so a re-run changes nothing (`--rotate` for new ones). It refuses any context but the laptop's (`MINIKUBE_PROFILE`): these values only open the emulators. On AKS the same names come from Key Vault through the CSI driver and workload identity (M5).

## D27 — The first tenant on the laptop: ticket triage
- What runs where: in namespace `triage`, from one image (`ghcr.io/salmanamn/ticket-triage`, CI-built, scanned, SBOM; ticket-triage-agent D28–D31): `triage-http` (ingest API, Event Grid webhook, queue depth; 1 replica), `triage-worker` (the Service Bus trigger; KEDA 0–2), and the lab pods `triage-lab-llm` (the fake LLM: M3 proves the hosting, not the model; Project 3's D12 measured quality) and `triage-lab-eventgrid` (the Event Grid stub). On the laptop, outside the cluster: Service Bus, Cosmos (database `triage-p7`, seeded with the fake LLM's embeddings), Azurite and Mailpit, on minikube's network (D23).
- Scaling stand-in: KEDA's Service Bus scaler can't read the emulator's queue length (ticket-triage-agent D29: its admin client calls HTTPS 443, the emulator serves no management API there), so on the laptop KEDA's `metrics-api` scaler polls `GET /api/queue-depth` on `triage-http` with its own host key (D22, D24). On AKS the same ScaledObject uses `azure-servicebus` with workload identity (M7).
- triage's `limits.memory` quota goes from 3 Gi to 4 Gi: the release at full scale is 2.3 Gi of limits, and a rolling update of the worker adds 0.75 Gi on top (unit test).

## D28 — The tenant check
- `scripts/check_triage.py` (evidence `docs/evidence/m3-triage.txt`): **keda** (three deployments available; its operator may read Secrets in `keda` and not in `triage`; the ClusterTriggerAuthentication present), **tenant** (the tenant's deployments available, the ScaledObject ready, the worker at 0), **network** (from a `triage-http` pod: the four emulator ports open, an unlisted port in the range, the Docker gateway, the internet and the API server closed), **e2e** (through `kubectl port-forward`: Project 3's E02, E03, E14 submitted with the host key → 202; KEDA scales the worker from 0; each ticket triaged, read from the worker's log; E02 → one `[HIGH]` email, E14 → one `[REVIEW]`, E03 → none, from Mailpit's API; the worker back to 0 after the cooldown).
- Same rules as D20 and D21: one line per check, evidence with ids, labels and subjects only (no `@`), nothing written from a cluster that stopped answering. M2's checks are re-run on the M3 cluster (`m3-admission.txt`, `m3-tenancy.txt`).
